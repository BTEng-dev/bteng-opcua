# Example: a scenario with no integration code

This folder is a **miniature project** showing the recommended layout. You write
a spec and a tree; everything in between is generated. No Python.

```
examples/
├── demo_server.py       # a stand-in OPC UA server — run this first
├── config/
│   ├── harvest.yaml     # you write: where the model is + which nodes you want
│   └── nodes.yaml       # generated by `bteng-opcua harvest` (committed)
└── trees/
    └── demo_tree.xml    # the scenario, addressing nodes by alias only
```

In a real project, `demo_server.py` is replaced by your actual OPC UA server;
`config/` and `trees/` look exactly like this.

## Run it — three commands

```bash
# 1. Start the demo server (leave it running in its own terminal)
python examples/demo_server.py

# 2. Read the server's information model and generate the registry
bteng-opcua harvest -s examples/config/harvest.yaml -o examples/config/nodes.yaml

# 3. Run the behaviour tree(s) against the generated registry
bteng-opcua run examples/trees/ -n examples/config/nodes.yaml
```

Expected result:

```
Tree finished: SUCCESS
  current_temp = 611.5
  setpoint_readback = 42.5
  move_result_code = 0
```

## What each file does

- **`config/harvest.yaml`** — the only hand-written data file. Names the server
  (`opc.tcp://127.0.0.1:4840/bteng/`) and the subtree to harvest
  (`Objects/Robot`). Aliases default to the snake-cased BrowseName.

- **`config/nodes.yaml`** — generated. Its `nodes:` section (addresses, data
  types, the `move_to_position` method signature) is written by `harvest` and
  should not be hand-edited. Its `blackboard:` section *is* hand-written and is
  **preserved** every time you re-harvest — `bteng-opcua run` reads it to seed
  the method's input arguments.

- **`trees/demo_tree.xml`** — the scenario: connect, guard on `robot_ready`,
  read `temperature`, write `setpoint`, call `move_to_position`, disconnect.
  Nodes are referenced by alias, so no node IDs or data types appear here.

## Offline variant (no server)

`demo_server.py --export models/robot.NodeSet2.xml` writes the same model as a
NodeSet2 file. Point `nodeset:` at it in `harvest.yaml` to generate the registry
without a running server.

See [`../docs/authoring-nodes.md`](../docs/authoring-nodes.md) for the full guide.
